### MarinaView

`class MarinaView : ComponentBase, IAsyncDisposable`

Blazor WebAssembly component that renders a `MarinaVisualizer` into a WebGL 2 canvas.

The view draws only while something changes or moves (see `MarinaVisualizer.NeedsRedraw` and `MarinaVisualizer.IsAnimating`), and not at all while it is scrolled out of sight or its tab is hidden, so a still marina costs nothing. `MarinaView.ContinuousRendering` makes it draw every display frame regardless. The popup's look comes from `_content/VirtualMarina.Blazor/marinaView.css`, which the script links into the page by itself. Its rules sit in the `virtualmarina` cascade layer, so any rule of the host's for the `vm-popup` classes wins over them. A page with a strict Content-Security-Policy can reference the file itself with a `<link rel="stylesheet">`; the script then leaves it alone.

| `MarinaStyle? MarinaStyle { get; set; }` | How the marina is drawn and animated (lighting, waves, status colors, boat opacities, land and trees, piers, labels, selection, camera). <a id="webglscenerenderer"></a>
### WebGlSceneRenderer

`sealed class WebGlSceneRenderer : ISceneRenderer, IDisposable`

`ISceneRenderer` backed by WebGL 2 through synchronous JS interop (Blazor WebAssembly).

Everything crosses the boundary as raw bytes (`byte[]`, which Blazor hands to JavaScript as a `Uint8Array` without Base64): meshes once per mesh, a layer's instances only when that layer changed, and then only the instances that changed. Every mesh is drawn instanced, one draw call per batch of a layer (see `RenderLayer.Batches`). Per frame, one buffer of 82 floats carries the camera, lighting, water and time uniforms, the reference image's placement and the popup's anchor; waves, bobbing and pulses animate on the GPU. Transparent instances are drawn back to front, as the OpenGL backend draws them: `TransparentSorter` orders them here, and the ordered instances are sent only when the camera or the scene moved and the order came out different from the one the script already has. `[JSImport]`/`[JSExport]` would save the JSON wrapper of each call, but it only exists in the browser runtime and would replace the module object the component and its tests talk to, so the calls stay on `IJSInProcessObjectReference`.

| Member | Description |
|---|---|
| `string BackendName { get; }` | Human-readable backend name, e.g. "OpenGL 3.3 Core (OpenTK)". |
| `string? DeviceDescription { get; }` | GPU renderer and WebGL version reported by the browser, available after `WebGlSceneRenderer.Initialize`. |
| `void Dispose()` | Stops rendering. GPU resources are released when the view is destroyed on the JS side. |
| `void Initialize()` | Compiles shaders and sets up global state. The graphics context must be current. |
| `void Render(RenderFrame frame)` | Draws one frame produced by `MarinaVisualizer.BuildRenderFrame()`. |
| `void Resize(int pixelWidth, int pixelHeight)` | The JS side sizes the canvas drawing buffer from its CSS size and devicePixelRatio. |

<a id="imarinavisualizer"></a>
### IMarinaVisualizer

`interface IMarinaVisualizer`

The API the host application (typically an ERP) uses to drive the 3D marina: layout, berth status, selection, tooltips and actions, camera and appearance. It is UI-framework and graphics-API agnostic: the same instance drives the WinForms/OpenGL view (`MarinaViewControl`) and the Blazor/WebGL view (`<MarinaView>`).

Threading. Not thread-safe. Call it from the UI thread that owns the view (marshal with `Control.BeginInvoke` in WinForms or `InvokeAsync` in Blazor when data arrives on a background thread). Events. Raised synchronously on the calling thread, after the state change has been applied, so handlers can read the new state and call back into the API. Snapshots. `Berth`, `Pier`, `Boat`, `Divider` and `MultiBerth` are immutable records. Getters and events return snapshots; change state only through this API. The exception is `Berth.ExternalData`, a mutable bag for host data shared by all snapshots of a berth. Ids of piers, berths, dividers, multi-berths and land areas are compared case-insensitively. Implementing this interface is not supported: it describes what `MarinaVisualizer` offers, and members are added to it in feature releases, which would break an outside implementation. Depend on it to keep host code testable — a mocking library fills in new members by itself — but let `MarinaVisualizer` be the only real implementation. `ISceneRenderer` is the interface meant to be implemented outside the library; anything added to that one comes with a default implementation. See `Docs/16-compatibility.md`. Custom views. This interface is what a host application uses. A view of its own — one that draws the marina and forwards input — works with the concrete `MarinaVisualizer` instead, for `MarinaVisualizer.Input`, `MarinaVisualizer.Update`, `MarinaVisualizer.BuildRenderFrame` and `MarinaVisualizer.SetViewportSize`.

<a id="marinalocalization"></a>
### MarinaLocalization

`static class MarinaLocalization`

The language of every piece of text the visualizer, the designer and the host panels display.

Text lives in a `Strings.resx` per assembly and is looked up through `CultureInfo.CurrentUICulture`, so an application that already sets the UI culture needs nothing here. `MarinaLocalization.Culture` is the one-line way to set it for the whole application, including threads started later. Adding a language means adding a `Strings.<culture>.resx` next to the neutral file (see `Docs/15-localization.md`); a culture without a translation falls back to the neutral English text, so nothing ever comes out blank.

<a id="marinadesigner"></a>
### MarinaDesigner

`sealed class MarinaDesigner`

Interactive layout designer: draw land areas as polygons, draw piers, add berths along piers, put boats ashore on land berths, plant trees and erase elements directly in the 3D view, with undo and redo, optionally tracing a calibrated aerial image. Available as `MarinaVisualizer.Designer`.

Turn it on with `MarinaDesigner.IsActive` and pick a `MarinaDesigner.Tool`. While active, clicks go to the designer instead of selecting berths; dragging, the wheel and the keyboard still move the camera. The host views (and the ready-made designer panels for WinForms and Blazor) forward input as usual, so no extra wiring is needed. Everything the designer creates goes through the normal API (`AddLandArea`, `AddPier`, `AddBerths`, ...), so `LayoutChanged` is raised as well as the designer's own events, and every change it makes can be taken back with `MarinaDesigner.Undo` (Ctrl+Z in the views) and made again with `MarinaDesigner.Redo` (Ctrl+Shift+Z or Ctrl+Y). Use `MarinaVisualizer.ExportObjects` or `MarinaVisualizer.GetLayout` to save the result. Coordinates: north is −Z (plan −Y) and east is +X, so an image with north at the top lies unmirrored under a camera with yaw 0 (see `MarinaDesigner.ViewTopDown`).

| `const int MaxUndoSteps = 50` | How many changes `MarinaDesigner.Undo` can step back through (older ones are dropped). |

### PreviewFleet

`static class PreviewFleet`

Picks the boats that fill a marina to a given share of its berths, for judging the look of a design against.

Two things make the result worth looking at rather than merely present. Each boat is chosen to suit the berth it goes in, so a twelve-metre berth does not end up with a jet ski rattling around in it; and a boat too wide for one berth, a catamaran above all, is moored across two berths side by side rather than left out. It works entirely from the Core domain model, so both the WinForms and the Blazor designers fill their preview fleets from this one copy rather than each carrying its own.

<a id="referenceimage"></a>
### ReferenceImage

`sealed class ReferenceImage`

A picture (typically a top-down aerial or satellite screenshot of the real marina) shown under or over the scene while designing, so the layout can be traced on it. North is at the top of the image.

The core library has no image codecs, so the host supplies the pixels: either decoded RGBA (`ReferenceImage.ctor`, e.g. from a WinForms `Bitmap`) or the original PNG/JPEG bytes plus the pixel size (`ReferenceImage.FromEncoded`, which the browser decodes). Every renderer accepts RGBA; the WebGL renderer also accepts encoded data. Instances are immutable: the constructors copy the buffers they are given, so changing the caller's array afterwards changes nothing here. Create a new one to change the picture. The arrays `ReferenceImage.Rgba` and `ReferenceImage.EncodedData` hand out are the image's own and must be treated as read-only.

### Berth

`sealed record Berth`

A single berth: a water berth along a pier (`Berth.PierId`), or a land berth on a `LandArea` (`Berth.LandAreaId`) where a boat is stored or maintained ashore. Immutable: the visualizer stores snapshots and hands them out in events, so host code can never change marina state without going through the API.

The one deliberate exception is `Berth.ExternalData`, a mutable bag shared by every snapshot of the same berth, where host code can keep its own objects. Equality compares everything else by value (the `Berth.Metadata` by its entries) and the bag by reference, so two snapshots of the same berth are equal while two berths built separately, each with a bag of its own, are not.

<a id="marinetraffic"></a>
### MarineTraffic

`sealed record MarineTraffic`

Passing traffic out at sea: vessels running along lanes that sweep past the marina from one edge of the map to the other, appearing far out, crossing the bay and leaving on the far side.

It is decoration, not layout: the vessels are not berths and cannot be clicked. Only these settings are stored — the lanes are worked out from the shoreline and the traffic from `MarineTraffic.Seed`, so a busy sea costs no more to store than an empty one. Where the lanes go. A lane is drawn through three points: one at each edge of the map, out where the mainland ends, sitting `MarineTraffic.EdgeClearance` off the coast; and one in the middle, passing the marina at `MarineTraffic.Clearance`. It curves smoothly between them, so a lane sweeps in towards the marina and back out again. Further lanes step out to sea from the first by `MarineTraffic.LaneSpacing` on average. Which way they run. Every vessel in a lane runs the same way, so nothing ever meets head-on. One or two lanes run opposite ways, as a traffic separation scheme does; beyond that the directions are drawn at random. How many there are. The full `MarineTraffic.MaximumVessels` is out there to begin with, scattered at random along the lanes, so the sea is busy from the first frame. As each one leaves the map another appears after about `MarineTraffic.SpawnDelaySeconds` — on a lane of its own, of a different kind, at its own speed and its own offset within the lane.

<a id="shoreline"></a>
### Shoreline

`sealed record Shoreline`

The mainland behind the marina: an open line of points whose first and last segments run on for ever, splitting the plan in two, with one side of it being land. It is what stops a marina looking like an island in an empty sea.

Two points are enough — that is simply a straight coast. More points bend it into bays and headlands. The line is open, not a ring: the segment before the first point and the segment after the last one carry on outward without end, so the land behind them never runs out however far the camera pulls back. Which side. `Shoreline.LandOnLeft` picks the half. "Left" is meant in plan coordinates, with plan Y as world Z: true puts the land on the side reached by turning the line's direction from +X toward +Z, so a line running east (+X) has its land to the south (+Z). Seen from above, where north (−Z) is up and east to the right, that is the right-hand side of someone walking the line from the first point to the last — the side `Pier.Right` points to for a pier running the same way. A designer chooses it by clicking the side that should be land. The rules. The line, carried on without end at both ends, must split the plan cleanly in two, or "the land side" means nothing: the drawn line must not cross or touch itself, the endless segments must not cross each other, and neither may run back across the drawn line. `Shoreline.Validate` reports each of these. (Up to this version a line crossing itself was allowed, and drew land in the wrong places; a design holding one now fails to load with that message, as a land area crossing itself always has.) It is drawn beneath the land areas placed by hand, so a quay traced along the shore sits on top of it and the two read as one piece of ground.

Capturing the outlines once, into the design, means the marina looks the same on a machine that has never heard of the font — which matters, because the machine that draws a marina and the machine that shows it to customers are rarely the same one. It also means the web view gets the same lettering as the desktop one. Only the characters that were captured can be drawn. `LabelFontDefinition.TryGetGlyph` says whether one was, and a caller that needs a character the font does not carry should fall back to `GlyphFont`.

<a id="labeltypeface"></a>
### LabelTypeface

`enum LabelTypeface`

The shape of the letters themselves, as against `LabelFont`, which is their weight and width. The two are chosen separately, so any typeface can be had bold or condensed.

<a id="marinetrafficfield"></a>
### MarineTrafficField

`sealed class MarineTrafficField`

The traffic actually out on the water: which vessels are on which lanes, where along them they have got to, and when the next one is due.

<a id="marinetrafficplanner"></a>
### MarineTrafficPlanner

`static class MarineTrafficPlanner`

Lays out the lanes the passing traffic runs along.

A lane is drawn through three points and curved smoothly between them: one at each edge of the map, out where the mainland ends and `MarineTraffic.EdgeClearance` off the coast, and one in the middle passing the marina at `MarineTraffic.Clearance`. So a lane sweeps in towards the marina and back out again, and both its ends are far enough away that a vessel appears and disappears out of sight. Three points is the whole of it. Pushing the coastline itself out to sea, which is what this used to do, folds over on itself wherever the coast turns in — a bay narrower than the push becomes a loop — and the lane came out with a right-angle kink in it and a six-kilometre jump between its first two points. Lanes beyond the first step out to sea by `MarineTraffic.LaneSpacing` on average, give or take, so they are not ruled parallel. Every vessel in a lane runs the same way and nothing meets head-on; one or two lanes run opposite ways, and beyond that the directions are drawn at random.

The view only takes keys nobody else would want: arrows, W/A/S/D, +/−/=, PageUp/PageDown, Home, Escape, Enter, Backspace and Delete, pressed on their own or with Shift (which turns panning into orbiting). The exceptions are Undo and Redo. Ctrl+Z (Cmd+Z in a browser, which hosts report as `InputModifiers.Control`) maps to `MarinaKey.Undo`; Ctrl+Shift+Z (Cmd+Shift+Z) and Ctrl+Y map to `MarinaKey.Redo`. They are a fallback for a host that has no Undo or Redo shortcut of its own: a host that does (an Edit ▸ Undo menu item, say) sees the key first and the view never gets it. Movement letters are matched by where they sit on the keyboard, not by what they type, so W/A/S/D is the same square on an AZERTY or a Cyrillic layout. Undo and Redo follow the letter printed on the key, as every application's Ctrl+Z does, falling back to the key's position only on a layout without Latin letters.

<a id="iscenerenderer"></a>
### ISceneRenderer

`interface ISceneRenderer : IDisposable`

The only contract a graphics backend must implement. The core library works out what to draw (`RenderFrame`); a backend (desktop OpenGL, WebGL, and later Vulkan, WebGPU, etc.) decides how.

Backend responsibilities: Upload every mesh in `RenderFrame.Meshes` (by id) and re-upload when `RenderFrame.MeshLibraryVersion` changes. Draw opaque objects, then the water grid with the water shader, then transparent objects with blending and depth writes off. Either draw `RenderFrame.Layers` batch by batch with `ShaderSources.InstancedModelVertex`, uploading a layer again only when its versions say so (`LayerUploadTracker` does the bookkeeping), or draw `RenderFrame.Objects` one by one with `ShaderSources.ModelVertex`. Apply the frame uniforms (camera, lighting, water, time) to the shaders in `ShaderSources`. All calls happen on the thread that owns the graphics context. This interface is meant to be implemented outside the library, so anything added to it in a later version comes with a default implementation that keeps existing backends compiling and working unchanged (see `Docs/16-compatibility.md`).

| Member | Description |
|---|---|
| `string BackendName { get; }` | Human-readable backend name, e.g. "OpenGL 3.3 Core (OpenTK)". |
| `string? DeviceDescription { get; }` | The graphics device actually in use once `ISceneRenderer.Initialize` has run, e.g. "NVIDIA GeForce RTX 3060 — OpenGL 4.6.0", or null when the backend cannot report one. Hosts show it in a status bar or an About box. |
| `void Initialize()` | Compiles shaders and sets up global state. The graphics context must be current. |
| `void Render(RenderFrame frame)` | Draws one frame produced by `MarinaVisualizer.BuildRenderFrame()`. |
| `void Resize(int pixelWidth, int pixelHeight)` | Framebuffer size in device pixels. |

<a id="renderlayer"></a>
### RenderLayer

`sealed class RenderLayer`

One part of the scene: its instances grouped into `RenderLayer.Batches` by mesh and pass, with version numbers that tell a backend what, if anything, it has to upload again.

A backend keeps, per layer kind, the `RenderLayer.LayoutVersion` and `RenderLayer.Version` it last uploaded. A different `RenderLayer.LayoutVersion` means the instances or batches were laid out afresh: upload everything. The same `RenderLayer.LayoutVersion` with a different `RenderLayer.Version` means some instances were rewritten in place; `RenderLayer.TryGetChangesSince` says which, so only those need to be sent. Versions come from one counter for the whole process, so a layer from another visualizer never looks like one already uploaded. The layer object is reused frame after frame and changes only while the visualizer builds a frame: read it on the thread that builds frames.

| `ReadOnlyMemory<RenderObject> Instances { get; }` | The instances, batch by batch (see `RenderLayer.Batches`). |

### ShaderSources

`static class ShaderSources`

Shared GLSL for every OpenGL-family backend. The bodies are written in the common subset of GLSL 330 and GLSL ES 300; only the version/precision header differs. That keeps the waves, shading and GPU animation identical on desktop and in the browser.

### MarinaDocument

`sealed class MarinaDocument`

A whole marina in one file: its layout (land areas, piers, dividers, berths and multi-berths), how it is drawn and animated (water, waves, lighting, status colors, labels, camera) and the designer's tool settings. Saved as JSON by the designer and loaded by the host application, so personalization travels with the design instead of living in host code.

The format is `{ "format": "virtualmarina.marina", "formatVersion": "1.0", ... }`. Reading is deliberately forgiving so files survive version changes in both directions: Missing properties fall back to the current defaults, so files written by older versions keep working. Properties this version doesn't know are kept in `MarinaDocument.Extensions` (document level) or alongside the element they belong to, and written back out, so a newer file survives a round trip through an older application. Unknown enum names fall back to the default instead of throwing. A file whose major version is newer than `MarinaDocument.CurrentVersion` is refused unless you pass `allowNewerVersion`: its meaning can't be guessed. A file written by an older version is brought up to date as it is read, one version step at a time, so the document always holds the current format; saving it writes the current format. Files are read and written as UTF-8. The `MarinaDocument.Parse`, `MarinaDocument.LoadAsync`, `MarinaDocument.SaveAsync` and `MarinaDocument.ToUtf8Bytes` members work on bytes and streams directly, which matters for a design carrying a large tracing photo; the string members are wrappers around them. `ISceneRenderer` for desktop OpenGL 3.3 core profile.

The host must make its GL context current before calling any member (including `OpenGlSceneRenderer.Dispose`) and must have loaded OpenTK's bindings (OpenTK's GLControl and GameWindow do this automatically). The designer's reference image must carry decoded RGBA pixels (`ReferenceImage.Rgba`); encoded-only images are skipped. Every mesh is drawn instanced: one draw call per batch of a `RenderLayer` (see `RenderLayer.Batches`), with each layer's instances in a buffer of their own that is uploaded again only when the layer changes, and then only the instances that changed. Transparent instances are sorted back to front whenever the camera or the scene moves.

| Member | Description |
|---|---|
| `OpenGlSceneRenderer()` | Creates an instance with default values. |
| `string BackendName { get; }` | Human-readable backend name, e.g. "OpenGL 3.3 Core (OpenTK)". |
| `string? DeviceDescription { get; }` | GL_RENDERER / GL_VERSION of the active context, available after `OpenGlSceneRenderer.Initialize`. |
| `bool IsInitialized { get; }` | True once shaders are compiled. |
| `void Dispose()` | Deletes GPU meshes and shader programs. The GL context must be current. |
| `void Initialize()` | Compiles shaders and sets up global state. The graphics context must be current. |
| `void Render(RenderFrame frame)` | Draws one frame produced by `MarinaVisualizer.BuildRenderFrame()`. |

### MarinaDesignerPanel

`sealed class MarinaDesignerPanel : UserControl`

Ready-made tool panel for `MarinaDesigner`: design mode, tools (land area, pier, berths, land berths, trees, erase), their settings, undo, and the reference image (load, opacity, move, scale calibration). ### MarinaViewControl

`sealed class MarinaViewControl : UserControl`

Drop-in WinForms control that renders a `MarinaVisualizer` with OpenGL, and shows the selection tooltip / actions window above the selected berth.

The view draws only while something changes or moves (see `MarinaVisualizer.NeedsRedraw` and `MarinaVisualizer.IsAnimating`), in step with the display, and not at all while its window is minimized or hidden; `MarinaViewControl.ContinuousRendering` makes it draw every frame regardless. The visualizer is not thread-safe: call `MarinaViewControl.Marina`'s members on the UI thread. If a status update does arrive on another thread anyway, the control marshals what it does in response (redrawing, the popup, the events it forwards) onto its own thread.
